# 2611-06. Data I/O is done by registered loader and saver classes that become nodes in the DAG

**Status:** Reconstructed from codebase (data adapters decided 2023-04 in [apache/hamilton#128](https://github.com/apache/hamilton/pull/128) / commit [f4eafcaf](https://github.com/apache/hamilton/commit/f4eafcaf36ddbb4fffe643553aff055f53c39a5d); driver-level materialization specified 2023-07 in [#235](https://github.com/apache/hamilton/issues/235) and merged 2023-08 with [#220](https://github.com/apache/hamilton/pull/220) / commit [134b7ecc](https://github.com/apache/hamilton/commit/134b7ecc2623bc40ff512e14fe78d380fc644250))

## Context

Before this, users loaded and saved data inside node functions or in driver code. [`docs/concepts/materialization.rst:52-56`](https://github.com/apache/hamilton/blob/ef88b1e96140a01f3d72967316c2335f8b62a067/docs/concepts/materialization.rst#L52-L56), written in 2024 with `Builder.with_materializers()` ([2924ed0e](https://github.com/apache/hamilton/commit/2924ed0e3323489554f3017c2ebb046a1592177e), #911), names the three limitations the design "aims to solve". **Redundancy**: deduplicate loading and saving code. **Observability**: include loading and saving in the dataflow, the directed acyclic graph (DAG) Hamilton builds, so that it can be seen and hooked. **Flexibility**: change loading and saving behavior without editing the dataflow. The design document anticipated the last one: "connections should be injected. they're execution time specific, i.e. instantiated at driver time." The design's author set out the reasoning at length in a 2023-11 blog post linked from `examples/decoupling_io/README.md`, "[Separate data I/O from transformation](https://blog.dagworks.io/p/separate-data-io-from-transformation)", which calls materializers "the primary tool we will leverage to separate I/O from transformations".

The spec on #235 lists the requirements for driver-level materialization. It "actually modifies the DAG so we get nodes that are traceable/manageable", "reuses the data adapter framework", "is simple/easy to call", "handles more than just pandas", "handles API keys for saving in a graceful way", and "Handles custom joining of results prior to saving".

This record was reconstructed from commit [f4eafcaf](https://github.com/apache/hamilton/commit/f4eafcaf36ddbb4fffe643553aff055f53c39a5d) (2023-04-01, "Adds implementation of data loaders"), the [spec comment on issue #235](https://github.com/apache/hamilton/issues/235#issuecomment-1650793866) (2023-07-26), commit [134b7ecc](https://github.com/apache/hamilton/commit/134b7ecc2623bc40ff512e14fe78d380fc644250), the issues and pull requests named below, [`docs/concepts/materialization.rst`](https://github.com/apache/hamilton/blob/ef88b1e96140a01f3d72967316c2335f8b62a067/docs/concepts/materialization.rst), [`hamilton/io/data_adapters.py`](https://github.com/apache/hamilton/blob/ef88b1e96140a01f3d72967316c2335f8b62a067/hamilton/io/data_adapters.py), and [`hamilton/registry.py`](https://github.com/apache/hamilton/blob/ef88b1e96140a01f3d72967316c2335f8b62a067/hamilton/registry.py#L220-L233). Materialization was built in [#236](https://github.com/apache/hamilton/pull/236), which merged into the `orchestration` branch, and reached `main` with #220. The bodies of #128 and #236 are unfilled templates, their reviews cover only documentation and naming, and #220's body says only "See commit history". The design document linked from [apache/hamilton#46](https://github.com/apache/hamilton/issues/46) (migrated from [stitchfix/hamilton#197](https://github.com/stitchfix/hamilton/issues/197)) is titled "SQL/DBT Integration"; it is about database connections rather than data adapters in general, and its comments carry no authors or dates.

## Decision

- A data loader or saver is a dataclass that subclasses `DataLoader` or `DataSaver` (`hamilton/io/data_adapters.py` lines [132](https://github.com/apache/hamilton/blob/ef88b1e96140a01f3d72967316c2335f8b62a067/hamilton/io/data_adapters.py#L132) and [173](https://github.com/apache/hamilton/blob/ef88b1e96140a01f3d72967316c2335f8b62a067/hamilton/io/data_adapters.py#L173)). It is constructed from keyword arguments and declares a `name()` and the `applicable_types()` it handles. Hamilton checks that subclasses are dataclasses ([`AdapterCommon._ensure_dataclass`](https://github.com/apache/hamilton/blob/ef88b1e96140a01f3d72967316c2335f8b62a067/hamilton/io/data_adapters.py#L73-L79)), because it reads their fields as the decorator's parameters: "we validate that the data adapter class is a dataclass, and has constructor parameters that are compatible with the params to the decorator" ([apache/hamilton#150](https://github.com/apache/hamilton/issues/150), by the design's author, 2023-04).
- Adapters are registered by name in `registry.LOADER_REGISTRY` and `SAVER_REGISTRY`. One name, such as `parquet` or `csv`, maps to several classes. Hamilton chooses among them by the type the dataflow asks for, which is how one key works for pandas, polars, and other libraries ("a registry that specifies a mapping of key -> data loader classes, allowing us to polymorphically select them", [f4eafcaf](https://github.com/apache/hamilton/commit/f4eafcaf36ddbb4fffe643553aff055f53c39a5d)). Plugins register their own, as "small/lightweight extensions. Similar to the rest of the extension framework" ([apache/hamilton#151](https://github.com/apache/hamilton/issues/151)).
- Loading returns the data together with a metadata dict ([`DataLoader.load_data`](https://github.com/apache/hamilton/blob/ef88b1e96140a01f3d72967316c2335f8b62a067/hamilton/io/data_adapters.py#L139) returns `tuple[type, dict[str, Any]]`), so what was read and written can be tracked.
- The same adapters back every entry point: the `@load_from` and `@save_to` decorators, the `from_` and `to` builders, `Driver.materialize()`, and `Builder.with_materializers()`. `materialize()` adds loader and saver nodes to the graph and executes them, and does not perform input/output (I/O) outside the graph ([134b7ecc](https://github.com/apache/hamilton/commit/134b7ecc2623bc40ff512e14fe78d380fc644250): "This manipulates the DAG and calls the materialization node"); the joining of results the spec asked for is the materializer's `combine` result builder. `from_` came later, from [#311](https://github.com/apache/hamilton/issues/311) ("`save_to` is to `materialize` as `load_from` is to `inject`").
- The `@dataloader` and `@datasaver` decorators, added in 2024 ([#983](https://github.com/apache/hamilton/pull/983)) to have "inline loaders / savers and to expose metadata for them", are a separate, lighter path that does not use the registry. A user-written node function returns its data together with the same kind of metadata ([`docs/concepts/materialization.rst:79`](https://github.com/apache/hamilton/blob/ef88b1e96140a01f3d72967316c2335f8b62a067/docs/concepts/materialization.rst#L79)).

## Consequences

- Adding a data format means writing one dataclass and registering it, usually in a plugin extension (2611-05). It then works with every entry point. #235 states that goal: "Ideally we'd make it so if you add a new `DataAdapter` you could use it as a materializer."
- Loaders and savers are nodes, so lifecycle hooks (2611-07), visualization, and lineage see them like any other node. The documentation lists the cost for materializers added at execution time: they are visible with `Driver.visualize_materialization()` but cannot otherwise be introspected, and `Driver.materialize()` has a different call signature from `execute()` ([line 109](https://github.com/apache/hamilton/blob/ef88b1e96140a01f3d72967316c2335f8b62a067/docs/concepts/materialization.rst#L109)). Materializers given to the `Builder` avoid that cost, and the documentation now calls them "typically preferrable" ([line 114](https://github.com/apache/hamilton/blob/ef88b1e96140a01f3d72967316c2335f8b62a067/docs/concepts/materialization.rst#L114)).
- A loader's `applicable_types()` is part of its contract. When several classes under one name apply to the requested type, the most recently registered one wins with a logged warning ("the *last* in the list that applies", #150), and loaders that accept `Any` come last ([`resolve_adapter_class`](https://github.com/apache/hamilton/blob/ef88b1e96140a01f3d72967316c2335f8b62a067/hamilton/function_modifiers/adapters.py#L119-L148)). That ordering was a compatibility choice: on [#536](https://github.com/apache/hamilton/pull/536) the author wrote that "The 'proper' solution would be to change custom_subclass_check, but that has the possibility of breaking some cases of materialization". Registration order is therefore observable behavior.
- Materializers are generated dynamically from the saver registry, so adapters registered at runtime become available, and import order does not matter ([#523](https://github.com/apache/hamilton/pull/523), fixing [#521](https://github.com/apache/hamilton/issues/521); its author pointed to code completion in a notebook as a way to discover the available materializers).

## Alternatives considered

From the #235 issue body ("Describe alternatives you've considered"), for where ad-hoc materialization happens:

- **At Driver construction time.** Listed and not chosen in 2023; the issue gives no reason. It was adopted in 2024 as `Builder.with_materializers()` ([#877](https://github.com/apache/hamilton/issues/877), built in [#911](https://github.com/apache/hamilton/pull/911)), alongside `Driver.materialize()`.
- **With `@save_to` only.** Already possible, but "often materialization is more of an ad-hoc operation", so a call on an existing Driver was added.
- **External to the Driver** (user code does the I/O). Already possible ("also doable") and not chosen. The issue gives no reason. Documentation written in 2024 ([`materialization.rst` at e00f1448](https://github.com/apache/hamilton/blob/e00f1448164d4d2923815d732caeede003d44f4a/docs/concepts/materialization.rst#L78-L79)) names the cost: it would "Lose the Hamilton benefits of having data loading and saving part of the dataflow (visualize, lifecycle hook, etc.)" and "Adds complexity to the Driver code".
