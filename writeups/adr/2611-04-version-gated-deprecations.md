# 2611-04. Deprecations name the major release that removes them, through a warn/fail version contract

**Status:** Reconstructed from codebase (decided 2022-07 in commit [d1edda18](https://github.com/apache/hamilton/commit/d1edda187e53dca77f537192fa3cf5f3958e3944), "Adds @deprecated decorator", merged 2022-08 in [stitchfix/hamilton#163](https://github.com/stitchfix/hamilton/pull/163))

## Context

The decorator was built to retire the `@parametrized*` decorators, which stitchfix/hamilton#163 replaced with `@parameterize`, `@parameterize_values` and `@parameterize_sources`: the author's checklist on that pull request includes "Add a `@deprecated` decorator for decorators" ([comment](https://github.com/stitchfix/hamilton/pull/163#issuecomment-1200063743)), and its first uses warned from 1.10.0 and failed from 2.0.0. Removal in 2.0 was already the practice by then: commit [b4e874bd](https://github.com/apache/hamilton/commit/b4e874bd9ffee327d4faccd8092712ff9c5ba537) (2022-04) put a plain log warning on `parameterized_input` saying "It will be removed in a 2.0.0 release." The decorator turned that convention into a contract the code checks.

The commit author "decided to build my own as I wanted to fully manage the lifecycle of items", and wrote that the mechanism "forces us into contracts. Though we can break them, I like the idea of making deprecations a planned event."

This record was reconstructed from commit [d1edda18](https://github.com/apache/hamilton/commit/d1edda187e53dca77f537192fa3cf5f3958e3944) (2022-07-30), the pull request that carried it, [stitchfix/hamilton#163](https://github.com/stitchfix/hamilton/pull/163) ("Full parametrized decorator", from the project's home before it moved to the Apache Software Foundation, merged 2022-08-15), and [`hamilton/dev_utils/deprecation.py`](https://github.com/apache/hamilton/blob/ef88b1e96140a01f3d72967316c2335f8b62a067/hamilton/dev_utils/deprecation.py). The commit message gives the reasoning. The decorator has since changed in [apache/hamilton#1802](https://github.com/apache/hamilton/pull/1802), [#1803](https://github.com/apache/hamilton/pull/1803) and [#1804](https://github.com/apache/hamilton/pull/1804); the Decision below describes it as it is now, and the Consequences say what those changes did.

## Decision

- An application programming interface (API) deprecation that carries a version contract goes through `hamilton.dev_utils.deprecation.deprecated`, a decorator for functions and callable classes. It takes `warn_starting`, `fail_starting`, `use_this`, `explanation`, and `migration_guide`.
- Its behavior depends on the installed Hamilton version (`hamilton.version.VERSION`). From `warn_starting` on, a call warns; from `fail_starting` on, it raises `DeprecationError`. Both bounds are inclusive ([`_should_warn` and `_should_fail`](https://github.com/apache/hamilton/blob/ef88b1e96140a01f3d72967316c2335f8b62a067/hamilton/dev_utils/deprecation.py#L178-L182) use `>=`), and a pre-release counts as its release, so 2.0.0rc1 fails too. The commit intended that from the start ("no funky versions or rc versions (the rc gets stripped)"), and in review the author agreed to test "the parser that strips it" ([review comment](https://github.com/stitchfix/hamilton/pull/163#discussion_r939754991)).
- The default `warn_action` issues a `FutureWarning` attributed to the code that called the deprecated API, so the standard `warnings` filters apply (`python -W error::FutureWarning` turns it into an error).
- A `fail_starting` of 1.0.0 or later must be a major release (`x.0.0`); one below 1.0.0 is exempt. In every case it must not come before `warn_starting` ([`_validate_fail_starting`](https://github.com/apache/hamilton/blob/ef88b1e96140a01f3d72967316c2335f8b62a067/hamilton/dev_utils/deprecation.py#L143-L152)).
- A deprecation without a replacement (`use_this=None`) must give a `migration_guide` ([`__post_init__`](https://github.com/apache/hamilton/blob/ef88b1e96140a01f3d72967316c2335f8b62a067/hamilton/dev_utils/deprecation.py#L132-L141)). A reviewer on stitchfix/hamilton#163 asked for "a clearer migration section that we can link to so people know what to do and until when" ([review](https://github.com/stitchfix/hamilton/pull/163#pullrequestreview-1064323389)), and the answer was a migration section in the decorator documentation ([83c3c6e0](https://github.com/apache/hamilton/commit/83c3c6e0d90ee1048366fe3e4dcbe112234976f9)).
- The docstring states the contract: "if you promise to deprecate something by X.0, then do it!" ([line 101](https://github.com/apache/hamilton/blob/ef88b1e96140a01f3d72967316c2335f8b62a067/hamilton/dev_utils/deprecation.py#L101)).

## Consequences

- A deprecation is a promise of the major version that removes the item. Current uses are in [`hamilton/driver.py`](https://github.com/apache/hamilton/blob/ef88b1e96140a01f3d72967316c2335f8b62a067/hamilton/driver.py#L606), [`hamilton/function_modifiers/expanders.py`](https://github.com/apache/hamilton/blob/ef88b1e96140a01f3d72967316c2335f8b62a067/hamilton/function_modifiers/expanders.py#L470), [`hamilton/function_modifiers/macros.py`](https://github.com/apache/hamilton/blob/ef88b1e96140a01f3d72967316c2335f8b62a067/hamilton/function_modifiers/macros.py#L255), and [`hamilton/telemetry.py`](https://github.com/apache/hamilton/blob/ef88b1e96140a01f3d72967316c2335f8b62a067/hamilton/telemetry.py#L29). All of them name `fail_starting=(2, 0, 0)`.
- Not every deprecation uses the decorator. Some call `warnings.warn` directly and carry no fail version, so nothing makes them raise in 2.0.0. They include module shims that issue a `FutureWarning` on import: [`hamilton/function_modifiers_base.py:25`](https://github.com/apache/hamilton/blob/ef88b1e96140a01f3d72967316c2335f8b62a067/hamilton/function_modifiers_base.py#L25), [`hamilton/plugins/polars_implementations.py:22`](https://github.com/apache/hamilton/blob/ef88b1e96140a01f3d72967316c2335f8b62a067/hamilton/plugins/polars_implementations.py#L22), and five modules in `hamilton/experimental/` ([`h_async.py:22`](https://github.com/apache/hamilton/blob/ef88b1e96140a01f3d72967316c2335f8b62a067/hamilton/experimental/h_async.py#L22), [`h_cache.py:35`](https://github.com/apache/hamilton/blob/ef88b1e96140a01f3d72967316c2335f8b62a067/hamilton/experimental/h_cache.py#L35), [`h_dask.py:22`](https://github.com/apache/hamilton/blob/ef88b1e96140a01f3d72967316c2335f8b62a067/hamilton/experimental/h_dask.py#L22), [`h_ray.py:22`](https://github.com/apache/hamilton/blob/ef88b1e96140a01f3d72967316c2335f8b62a067/hamilton/experimental/h_ray.py#L22), and [`h_spark.py:26`](https://github.com/apache/hamilton/blob/ef88b1e96140a01f3d72967316c2335f8b62a067/hamilton/experimental/h_spark.py#L26)). The `CacheAdapter` ([`hamilton/lifecycle/default.py:371`](https://github.com/apache/hamilton/blob/ef88b1e96140a01f3d72967316c2335f8b62a067/hamilton/lifecycle/default.py#L371)) and `DiskCacheAdapter` ([`hamilton/plugins/h_diskcache.py:108`](https://github.com/apache/hamilton/blob/ef88b1e96140a01f3d72967316c2335f8b62a067/hamilton/plugins/h_diskcache.py#L108)) constructors also issue a `FutureWarning`. `display_graph=True` (`hamilton/driver.py` lines [549](https://github.com/apache/hamilton/blob/ef88b1e96140a01f3d72967316c2335f8b62a067/hamilton/driver.py#L549), [641](https://github.com/apache/hamilton/blob/ef88b1e96140a01f3d72967316c2335f8b62a067/hamilton/driver.py#L641) and [717](https://github.com/apache/hamilton/blob/ef88b1e96140a01f3d72967316c2335f8b62a067/hamilton/driver.py#L717)) and `FunctionGraph.get_impacted_nodes` ([`hamilton/graph.py:1001`](https://github.com/apache/hamilton/blob/ef88b1e96140a01f3d72967316c2335f8b62a067/hamilton/graph.py#L1001)) issue a `DeprecationWarning` instead. Most of these messages name 2.0 as the removal release, but only in their text. The `polars_implementations`, `h_dask`, `h_ray`, and `h_spark` shims name no release. The shims began as log lines: the `function_modifiers_base` one comes from a reviewer's suggested `logger.warning` on [stitchfix/hamilton#237](https://github.com/stitchfix/hamilton/pull/237#discussion_r1032997523), and #1804 turned the seven shims and both cache adapters into `FutureWarning`s. Why they bypass the decorator is not recorded.
- Until #1802 both comparisons were strict (`>`), so an item with `fail_starting=(2, 0, 0)` would only have warned on 2.0.0 and first raised on 2.0.1, against the docstring's "by X.0". #1802 made them inclusive, so such an item raises on 2.0.0.
- Until #1804 the default `warn_action` was `logger.warning`, so `-W error` and pytest warning filters did not catch these warnings. #1804 made it a `FutureWarning`, and #1803 builds every message in one place: a warning reads "… is deprecated and will stop working in hamilton version: …".
- A deprecation that passes its own `current_version` freezes its clock. `pipe` and `dynamic_transform` did, and #1804 found that "`pipe` warned on every release, `dynamic_transform` never warned, and neither would ever fail". It removed the pins and added [`tests/test_deprecation_schedules.py`](https://github.com/apache/hamilton/blob/ef88b1e96140a01f3d72967316c2335f8b62a067/tests/test_deprecation_schedules.py), which fails when a production `deprecated(...)` call passes `current_version`. Both #1803 and #1804 leave one design question open: "Reading the version when the API is called would be a cleaner design, but it changes the decorator's interface and needs its own decision."
- Replacing this mechanism takes a record that supersedes this one (`writeups/adr/README.md`).

## Alternatives considered

- **An existing deprecation library or bare `warnings.warn`.** The commit says only that the author "decided to build my own", to manage the whole lifecycle. The body, comments and reviews of stitchfix/hamilton#163 name no deprecation library. The one third-party library the pull request mentions is wrapt, weighed for wrapping both functions and callable classes rather than as a deprecation library: commit [5e9a71f4](https://github.com/apache/hamilton/commit/5e9a71f40eb77f094c74b3bdd2306b749f8640ed), in the same pull request, says "a third party library like wrapt might help but I wanted to keep it simple."
- **A different warning category.** #1804 weighed `DeprecationWarning`, which "Python hides … by default unless the warning is attributed to `__main__`", and a Hamilton-specific subclass, rejected because "it adds a public name", and chose `FutureWarning`. A subclass named `RemovedInHamilton2Warning` had been proposed in a contributor's work plan on [apache/hamilton#918](https://github.com/apache/hamilton/issues/918#issuecomment-4692760418).
